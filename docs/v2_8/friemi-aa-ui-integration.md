# Friemi 聚吧详情页 × AA 核算：UI 迁移与平台融合方案

> 文档状态：UI 与平台适配方案定稿
> 更新日期：2026-09-11
> 目标页面：Friemi 聚吧详情页
> 逻辑依赖：[AA 计费器 v2.8：产品拆解与核心逻辑](./aa-billing-product-logic.md)

## 0. 结论先行

AA 不应作为一款独立财务 App 被塞进 Friemi，而应成为“聚吧”上下文中的原生协作工具。

最终结构确定为：

```text
聚吧详情页
├── 聚吧原有内容：标题、封面、时间、地点、费用属性
├── 参与者与工具条
│   ├── 聊天
│   ├── 详情
│   ├── 公告（替换旧概念稿中的“照片”入口）
│   └── 核算（AA 功能入口）
├── 公告预览
├── 发起人信息
└── 主理人管理操作

核算二级页
├── 本次活动与我的余额摘要
├── 明细
│   ├── 支出
│   ├── 收入
│   └── 转账
└── 结算
    ├── 推荐付款路径
    ├── 收款方式
    └── 全员结算进度
```

旧 AA 概念稿的六个独立页面将被压缩为“一张聚吧详情页入口 + 一个核算中心 + 三类任务页/弹层”，避免出现“App 里面又套一款 App”的割裂感。

## 1. 本文档边界

### 1.1 本文档负责

- 分析旧 AA 概念稿的视觉语言、信息层级和交互理念。
- 分析当前 Friemi 聚吧详情页的视觉和结构。
- 确定 AA 入口在聚吧详情页中的准确位置。

- 定义聚吧成员、主理人、游客与 AA 参与者的自适应映射。
- 定义不同用户、活动阶段和账务状态下的 UI。

## 2. 设计方向

本次视觉方向定义为：**社交聚会里的一本安静账本**。

它应该保留 Friemi 轻松、友好、有人情味的社交气质，同时让涉及金额的页面准确、稳定、可追溯。用户进入核算页后仍然感觉自己留在同一个聚吧里，而不是突然进入银行或企业报销系统。

设计关键词：

- 温和，而不是金融压迫感。
- 清楚，而不是表格堆叠。
- 透明，而不是复杂算法黑盒。
- 协作，而不是主理人单向收费。
- 原生，而不是外接工具跳转。

## 3. 旧 AA 系统的完整 UI 设计理念

### 3.1 原有信息架构

旧概念稿把完整流程拆成六步：

1. 从活动详情进入。
2. 查看结算总览和费用列表。
3. 上传开支或手动输入。
4. 确认参与人和分摊结果。
5. 查看付款路径与主理人收款方式。
6. 查看全员结算进度。

这个结构的优点是线性、容易讲解；缺点是每个步骤都被放大成独立页面，进入 Friemi 后会产生重复标题、重复成员信息和重复返回层级。

### 3.2 视觉语言

旧稿已经使用接近 Friemi 的品牌语言：

- 暖白背景，不使用冷灰金融后台底色。
- 深绿作为主要行动和完成状态。
- 珊瑚色表达警告、待处理和取消。
- 米色细边框、低阴影或无阴影卡片。
- 大圆角卡片、胶囊按钮、圆形头像和圆角线性图标。
- 金额使用较大字号，辅助信息保持克制。
- 人物插画用于解释“朋友一起分摊”，弱化算账的紧张感。

旧稿可识别的核心色彩方向为：

| 角色 | 建议沿用色值 | 用途 |
| --- | --- | --- |
| Friemi 深绿 | `#156240` | 主按钮、活动态、关键数字 |
| 友好绿 | `#369758` | 完成、确认、轻强调 |
| 珊瑚橙 | `#F09182` | 争议、警告、待处理 |
| 柔粉 | `#DEAAB3` | 非关键分类或装饰 |
| 淡蓝 | `#DEEBFF` | 信息提示 |
| 暖米色 | `#D6D5B2` | 分隔、描边、次级按钮 |
| 暖白 | `#FEFFF9` | 页面与卡片底色 |
| 墨黑 | `#1D1D1B` | 标题和正文 |
| 次级灰 | `#8E8383` | 辅助信息、未激活图标 |

正式实现应优先复用 Friemi 现有 Design Token；上表用于比对视觉方向，不新建第二套重复色板。

### 3.3 信息表达理念

旧稿采用了四层信息优先级：

1. 总支出与人均金额。
2. 已上传笔数、参与人数、结算人数。
3. 单笔开支与确认状态。
4. 分类、备注和付款方式。

同时强调三类透明度：

- 开支透明：每一笔费用有来源和状态。
- 分摊透明：参与人明确可见。
- 付款透明：所有参与者可以看到结算进度。

### 3.4 旧稿值得保留的设计

- 从活动上下文直接进入，不重新创建一个陌生群组。
- 总支出、参与人数、个人金额集中展示。
- 费用行同时显示金额、提交人、时间和状态。
- 上传凭证与手动录入并存。
- 分摊前明确列出参与者。
- 平台不经手资金，付款直接发生在参与者之间。
- 结算进度以成员为单位展示，适合多人活动收尾。
- 主理人也可以作为普通参与者承担费用。
- 活动实际支出与组织盈利明确分离。

### 3.5 旧稿不能直接照搬的部分

| 旧稿表现 | 问题 | 新方案 |
| --- | --- | --- |
| 独立的 Friemi Settlement 首页 | 与聚吧详情重复，像另一个产品 | 删除独立入口页，核算属于聚吧工具条 |
| 六个页面连续跳转 | 路径过长，返回关系复杂 | 一个核算中心承载总览，任务用二级页/底部弹层 |
| 默认突出“人均金额” | 只适合均分，不适合权重或自定义金额 | 优先显示“我的分摊/我的余额”；仅在真均分时显示人均 |
| “已上传 3 笔” | 上传不代表审核和入账 | 拆为“已计入”“待确认”“已驳回” |
| 所有人都向主理人付款 | 多付款人场景会算错结算路径 | 按核心结算算法给出实际债权人，不强制汇总给主理人 |
| 收款方式完整公开 | 可能泄露账户信息 | 只向存在付款关系的参与者显示必要信息 |
| 全靠绿、橙、红表达状态 | 色觉无障碍不足 | 状态色同时配文字、图标和辅助标签 |
| “照片”作为活动工具入口 | 与当前聚吧公告和信息结构不匹配 | 工具条第三项改为“公告”；收据照片留在费用内部 |
| 主理人参加使用单独开关 | 容易误认为所有费用都包含主理人 | 每笔费用的参与者选择决定主理人是否承担 |
| 只有欧元示例 | 无法表达旅行和本地人民币混用 | 金额组件支持 CNY 与多币种快照 |

## 4. 当前 Friemi 聚吧详情页分析

### 4.1 当前页面骨架

当前页面从上到下为：

1. 底部抽屉式页面的顶部拖拽指示。
2. 聚吧标题。
3. 大幅圆角封面图和右上角悬浮操作。
4. 人数、日期、地点、费用属性。
5. 群公告预览卡。
6. 发起人信息。
7. 已报名成员。
8. 编辑聚吧、群聊、取消聚吧、添加游客等管理操作。

页面的优势是内容轻、图片区占主导、社交信息明显；缺口是“公告、群聊、报名成员和未来 AA”分散在不同位置，缺少一个稳定的聚吧工具导航。

### 4.2 当前视觉特征

- 白色或暖白底，留白充分。
- 黑色重字标题与大圆角活动照片形成主要视觉锚点。
- 深绿色用于主操作、图标和链接。
- 浅绿色描边按钮与珊瑚色危险按钮形成层级。
- 公告、发起人和成员使用卡片/列表混合布局。
- 顶部封面上的更多、分享、换封面和举报使用圆形悬浮按钮。

AA 融合必须服从这一层级，不能让金额卡比聚吧标题和封面更抢眼。

## 5. 聚吧详情页的最终改造

### 5.1 准确放置位置

新增“参与者与工具条”组件，位置固定在：

```text
聚吧封面与基础信息
↓
人数 / 日期 / 地点 / 免费或收费属性
↓
【参与者与工具条】← 新增 AA 入口的位置
↓
群公告预览
↓
发起人
↓
主理人管理操作
```

它位于费用属性下方、现有群公告卡上方，与用户提供的入口缩略图一致。

### 5.2 参与者与工具条结构

```text
┌────────────────────────────────┐
│ 参与者  6/8                  › │
│ ●  ●  ●  ●  ●              +1 │
├────────────────────────────────┤
│   聊天       详情       公告       核算   │
│   ◯          ◉          ◯•         ◯²    │
└────────────────────────────────┘
```

规则：

- 第一行复用当前“已报名”数据，显示已确认参与者、容量和头像。
- 点击头像区域进入完整参与者列表；主理人在该列表中添加游客。
- 第二行是四个等宽工具，不使用可横向滚动的入口。
- 当前所在模块使用深绿图标和文字，其余使用次级灰。
- `公告` 有未读内容时显示圆点，`核算` 有当前用户待处理事项时显示数量；角标永不显示具体金额。
- 组件使用 Friemi 暖米色细边框和现有卡片圆角，不使用缩略图外面的黄色标注框。

### 5.3 四个入口的最终命名与行为

| 入口 | 图标语义 | 点击行为 | 详情页状态 |
| --- | --- | --- | --- |
| 聊天 | 现有圆角对话气泡 | 打开本聚吧群聊 | 有未读消息时显示数量 |
| 详情 | 信息卡/列表 | 返回聚吧详情顶部 | 当前页默认激活 |
| 公告 | 铃铛或公告板 | 打开本聚吧公告列表；详情页公告卡是同一内容的预览 | 替换旧稿“照片”入口 |
| 核算 | 账单/钱包与勾选 | 打开本聚吧 AA 核算中心 | 有待确认/待付款时显示角标 |

“照片替换为公告”只发生在工具条入口。聚吧的大幅封面图继续保留；费用凭证照片继续存在于核算明细中，二者都不被删除。

### 5.4 消除当前页面重复入口

- 当前底部“群聊”大按钮移除，由工具条“聊天”统一承接。
- 当前“已报名”独立区块合并进“参与者与工具条”，避免成员头像出现两次。
- “添加游客”从页面底部迁入参与者列表的主理人操作，详情页底部不再保留重复按钮。
- 群公告预览卡继续保留；工具条“公告”负责定位或进入公告历史。
- “编辑聚吧”和“取消聚吧”仍属于主理人管理区，不放进四项工具条。

### 5.6 导航、返回与深链

- 四项工具分别指向同一个 `event_id` 下的聊天、详情、公告和核算路由，不创建脱离聚吧的顶层 AA 导航。
- 从详情页进入核算后，系统返回操作回到原聚吧详情页并恢复原滚动位置；从核算明细进入单笔交易，返回先回核算中心。
- 从通知进入费用、审核或付款详情时，先校验当前用户的聚吧身份与对象权限，再加载数据；校验失败只显示无权限/已失效状态，不回退展示缓存金额。
- 深链目标已作废、归档或删除时，页面显示对象当前状态并提供回到核算中心的出口，不能停留在无限加载。
- 切换聊天、公告和核算不会重置未提交的“记一笔”草稿；草稿留在原任务中并在返回时提示继续或放弃。
- 页面标题与系统分享链接始终使用聚吧名称；不得生成一个用户无法识别来源的孤立“AA 账本”链接。

## 6. AA 如何自适应嵌套进聚吧

### 6.1 数据关系

```text
Friemi Event
├── Event Organizer ──────> AA Owner
├── Event Co-organizer ───> AA Admin
├── Confirmed Attendee ───> AA Member / Participant
├── Added Guest ──────────> AA Guest Participant
├── Group Chat ───────────> AA 通知和讨论入口
├── Announcement ─────────> 核算规则、截止时间和变更通知
└── Event Lifecycle ──────> AA Ledger Lifecycle
```

AA 账本不要求用户重新建立群组。首次由主理人或参与者打开“核算”时，系统按 `event_id` 幂等创建一个关联账本。

关联规则固定如下：

- 一个聚吧在同一时间只能关联一个有效 AA 账本，数据库对 `event_id` 建立唯一约束；重复点击和多设备同时首次进入只能返回同一个账本。
- 只有已报名参与者或主理人首次进入时才创建账本；未报名访问者点击入口只看到权限说明，不能触发创建。
- 聚吧标题、封面、时间或地点变化只更新核算页的上下文展示，不改变 `ledger_id`、历史交易日期或余额。
- 聚吧所有权移交时，AA Owner 必须在同一业务事务中同步移交；失败时聚吧所有权也不完成变更，不能产生无主账本。
- 当前页面的“再来一局”会创建新的 `event_id` 和新 AA 账本。可以复制分类、核算开关和分摊偏好，但绝不复制交易、余额、付款请求、收款账号授权、审核状态或结算进度。
- 删除聚吧不能级联硬删除已有账务。没有任何提交或交易时可一并进入删除冷静期；已有账务时聚吧转入历史只读入口，参与者仍可完成退款、争议和结算。
- 主理人只能在没有费用提交、交易或付款请求时关闭核算入口；一旦产生账务痕迹，只能冻结或归档，不能隐藏参与者的历史访问权。

### 6.2 成员同步规则

- 账本没有有效交易前，参与者名单跟随聚吧报名状态自动同步。
- 只有 `ACTIVE` 账本中的新已确认报名者自动加入 AA 参与者名单，候补、申请中、已拒绝和已取消报名者不加入；新成员不会被自动加入历史费用。
- 账本进入 `FROZEN` 或 `ARCHIVED` 后，报名变化不再自动改变 AA 名单；如确需补录成员，Owner/Admin 必须先重新打开核算并通知现有参与者。
- 有历史交易后退出、被移除或未到场的人只转为 `INACTIVE`，不能从账务中物理删除。
- 新增游客生成稳定的 AA 参与者 ID；游客以后注册时可认领，不重建余额。
- 主理人只有在某笔费用的参与者列表中被选中时才承担该笔费用。
- 合并重复报名身份时，使用核心账务文档的参与者合并规则。
- 当聚吧已确认参与者超过核心上限 50 人时，不自动截取前 50 人。核算入口向主理人提示“AA 核算最多支持 50 位直接费用参与者”，由主理人在产生第一笔费用前明确选择最多 50 人；未被选择者看不到金额。超过 50 人的统一收费应进入大型活动收费能力，而不是绕过上限建立隐式子账本。

### 6.3 角色映射

| 聚吧身份 | AA 角色 | 默认能力 |
| --- | --- | --- |
| 发起人/主理人 | Owner | 管理成员、确认费用、开启结算、设置付款方式、处理争议 |
| 联合主理人 | Admin | 确认费用、协助结算、处理成员问题 |
| 已报名参与者 | Member | 查看透明账务、提交费用、确认自己的分摊与付款 |
| 主理人添加的游客 | Guest Participant | 由主理人代录或通过专属链接查看自己的部分 |
| 未报名访问者 | 无 AA 身份 | 只能看到“报名后可查看核算”，不能看到金额和成员余额 |

### 6.4 活动与核算生命周期映射

| 聚吧阶段 | 核算状态 | UI 行为 |
| --- | --- | --- |
| 招募中、暂无费用 | `ACTIVE / EMPTY` | 核算入口可见，显示说明和“记第一笔” |
| 活动准备/进行中 | `ACTIVE / RECORDING` | 允许提交费用，余额显示“预计” |
| 活动结束、主理人核对 | `FROZEN / REVIEWING` | 暂停普通成员新增，主理人确认待审费用 |
| 开始结算 | `FROZEN / SETTLING` | 固定当前账本版本，生成付款路径 |
| 部分成员完成 | `FROZEN / PARTIALLY_SETTLED` | 显示进度和待处理操作 |
| 全员结清 | `FROZEN / SETTLED` | 显示完成摘要，允许导出后归档 |
| 聚吧取消且无费用 | `ARCHIVED` | 直接归档空账本 |
| 聚吧取消但已有费用 | `FROZEN / REVIEWING` | 保留真实成本，先退款/结算再归档 |

结算过程中新增或修改已入账费用会使原结算建议失效。只有 Owner/Admin 明确选择“重新打开核算”后才能修改，并且所有受影响参与者收到通知。

### 6.5 Friemi 场景的审核适配层

核心 AA 引擎只计算 `POSTED` 交易。为了适应公开聚吧中参与者较多、彼此未必熟悉的情况，Friemi 在核心交易外增加提交审核层：

```text
成员提交费用
→ PENDING_REVIEW（不进入余额）
→ 主理人确认
→ 创建/更新核心 POSTED 交易
→ 进入余额与结算

PENDING_REVIEW
→ 主理人驳回
→ REJECTED（保留理由和审计，不进入余额）
```

- Owner/Admin 自己创建的费用默认直接 `APPROVED`，但仍保留修改记录。
- 参与者提交费用默认 `PENDING_REVIEW`，明细中清楚显示“尚未计入总额”。
- 主理人不能无痕修改参与者提交的金额；修改后必须显示原值，并由提交者收到通知。
- 小型熟人聚吧可以开启“成员提交后直接计入”，该配置只跳过审核，不改变核心算法。
- 提交者可以在 `PENDING_REVIEW` 阶段编辑或撤回；撤回后保留审计，但不进入余额。
- 已批准费用被普通参与者修改时，不直接覆盖 `POSTED` 版本，而是生成 `CHANGE_PENDING_REVIEW`；旧版本继续参与余额，管理员确认后才原子替换为新版本。
- 被驳回费用可修改后重新提交；重新提交生成新审核版本，不能把旧驳回状态改写成从未发生。
- 开始结算前必须把所有待审核、待变更和同步冲突处理为批准、驳回或撤回；存在未处理项时阻止冻结结算版本。

### 6.6 转账确认适配

Friemi 聚吧默认开启核心逻辑已经支持的“双向确认”：

```text
付款人标记已付
→ 已付款·待收款人确认
→ 收款人确认
→ 已结清

                    └→ 金额有误/未收到
                       → 有争议
                       → 主理人协助处理
```

这与通用 AA 产品“可立即入账”的默认配置不同，但属于核心能力允许的场景配置，不产生账务规则冲突。

### 6.7 组合状态不是第二套账务状态机

第 6.4 节中的 `EMPTY`、`RECORDING`、`REVIEWING`、`SETTLING`、`PARTIALLY_SETTLED` 和 `SETTLED` 是页面根据核心数据派生的 ViewModel 状态，不写回核心 `Ledger.status`。

```text
UI state = derive(
  ledger.status,
  approved_transaction_count,
  pending_review_count,
  conflict_count,
  non_zero_balance_count,
  pending_transfer_count,
  dispute_count
)
```

核心只保存 `ACTIVE / FROZEN / ARCHIVED / DELETION_PENDING / DELETED` 等正式状态以及交易状态。所有客户端必须调用同一派生规则，不能各自解释“已结清”。

### 6.8 适配层输入、输出与失败边界

Friemi 与 AA 核心只通过适配层交互：

```text
Friemi Event Domain
  ├─ event identity / title / lifecycle
  ├─ organizer and attendee roles
  └─ chat and announcement routes
              │
              ▼
       EventAAAdapter
  ├─ ensure one ledger
  ├─ map/sync participant identities
  ├─ manage review submissions
  ├─ derive UI state and badge
  └─ translate domain events
              │
              ▼
          AA Core
  ├─ transactions and revisions
  ├─ allocation and FX
  ├─ balances and settlements
  └─ payment/transfer states
```

适配层必须处理的聚吧事件：

- `EventCreated`
- `AttendeeConfirmed / AttendeeRemoved`
- `GuestAdded`
- `EventUpdated`
- `EventOwnershipTransferred`
- `EventCancelled / EventDeleted`
- `EventCloned`

AA 核心向 Friemi 输出：

- `ExpenseReviewRequired`
- `LedgerBalanceChanged`
- `SettlementActionRequired`
- `TransferConfirmationRequired`
- `SettlementDisputed`
- `LedgerSettled`

边界规则：

- Friemi 是聚吧身份与生命周期的权威来源；AA 是所有金额和结算事实的权威来源。
- 适配层只能调用核心命令，不能直接写余额或自行生成结算金额。
- 每个跨域事件包含唯一事件 ID，并按该 ID 幂等消费。
- 普通成员同步失败可以进入重试队列；所有权移交、删除和开启结算必须同步成功后才能向用户显示完成。
- 暂时无法连接 AA 核心时，详情页保留聚吧功能，但核算入口显示“暂时不可用/最后更新时间”，绝不展示推测金额。

## 8. 核算中心

### 8.1 页面层级

从详情页点击“核算”后进入同一聚吧下的二级页：

```text
←  核算                                      ···
   你的月亮我的串 · 9月26日

┌────────────────────────────────┐
│ 本次总支出               ¥428.00 │
│ 6 位参与者 · 已计入 5 笔 · 待确认 1 笔 │
│                                  │
│ 你需付                    ¥62.00 │
│                      [查看付款路径] │
└────────────────────────────────┘

        [ 明细 ]      [ 结算 ]

费用列表 / 成员结算进度

            [ ＋ 记一笔 ]
```

保留返回箭头、聚吧标题和日期作为上下文，不重复显示大幅活动封面。

右上角 `···` 按权限提供：核算规则、成员、付款方式授权、活动记录、搜索与筛选、导入导出、冻结/重新打开和归档。危险操作固定放在菜单底部并再次确认。

### 8.2 顶部摘要卡

信息优先级固定为：

1. 当前用户需要做什么：需付、应收、待确认或已结清。
2. 本次总支出。
3. 已计入笔数、待确认笔数和参与人数。
4. 主操作按钮。

主理人视角可额外看到“已结清 X/Y 人”；普通参与者默认先看到自己的金额。

只有当所有有效费用确实使用相同参与人并均分时，才显示“人均金额”。否则改为“你的分摊”，防止旧稿中的人均数字误导用户。

### 8.3 明细页签

费用行采用 Friemi 轻卡片/列表样式：

```text
[分类图标] 烤串与饮料                    ¥168.00
          小雨提交 · 今天 19:32
          4 人参与                    [已计入]
```

状态用词固定为：

- `待主理人确认`
- `已计入`
- `已驳回`
- `同步中`
- `有冲突`
- `已作废`

金额右对齐并使用等宽数字；状态放在次级位置，不能与金额争夺第一视觉层级。

明细超过首屏时提供搜索和筛选入口，支持类型、成员、分类、日期和状态。筛选结果必须显示“当前筛选”，并与账本总支出视觉分开，避免把局部合计误认为全局余额。

### 8.4 结算页签

普通参与者看到：

- 自己的应付/应收总额。
- 自己需要执行的付款路径。
- 与自己有关的付款状态和争议。
- 全组的结清人数摘要。

主理人看到：

- 全组结算进度。
- 待确认转账。
- 有争议记录。
- “提醒未结清成员”操作。

所有参与者都可查看已入账费用和公开的成员余额；收款账号、邮箱、二维码等敏感付款信息只向实际需要向该收款人付款的人展示。

同一主理人对同一成员的手动付款提醒最多每 24 小时一次；争议处理中不允许催付。提醒进入活动日志，成员可以静音核算提醒但不能关闭影响余额的变更通知。

## 9. 三个核心任务页

### 9.1 记一笔

旧稿“拍照上传/相册选择”不应成为第一页唯一入口。新顺序为：

1. 金额与币种。
2. 标题。
3. 谁付了。
4. 哪些人参与、怎么分。
5. 分类。
6. 可选的收据照片、日期和备注。

页面提供“拍收据”和“从相册选”作为辅助按钮。v2.8 不按金额强制上传凭证；没有照片也可以提交。以后增加凭证门槛属于新的聚吧规则，必须明确公示后才能启用。

### 9.2 选择分摊

成员行不能只显示“已包含”，还需要显示最终份额：

```text
✓ Lou（你）                             ¥36.00
✓ Kevin                                 ¥18.00
✓ Amy                                   ¥18.00
○ Tom                                    未参与
```

顶部切换：`均分 / 按份数 / 百分比 / 自定义金额`。底部固定展示合计、剩余差额和确认按钮。

### 9.3 付款与确认

付款详情先显示：

- 你向谁付款。
- 应付金额和币种。
- 为什么付给此人。
- 对方主动提供的付款方式。

支持复制文字、复制账号、展示二维码和标记已付款。Friemi 明确提示“款项直接转给参与者，Friemi 不经手资金”。

当多个人分别垫付时，付款方式来自结算算法确定的实际收款人，不能把所有钱默认导向主理人。

付款方式由用户在个人资料中维护，再按聚吧和实际结算关系授权展示。删除或更新个人付款方式不会改写已记录的转账；尚未付款的建议在打开时使用最新可用方式，无法提供方式时仍允许双方线下协商并手动确认。

### 9.4 收入、转账与历史操作入口

底部“＋ 记一笔”打开类型选择：

1. `记录支出`：默认首项，用于共同开支。
2. `记录收入`：用于退款、返现、押金退回和共同物品出售。
3. `记录转账`：用于补录已经发生、但不是从推荐结算发起的还款。

推荐结算中的付款确认会自动创建 Transfer，不要求用户再次手工录入。普通 Member 不能代录与自己无关的两人转账；权限规则继承核心文档。

点击任一明细进入交易详情，展示付款/收款人、参与者份额、汇率、附件、创建者和修订历史。允许的编辑、作废和恢复操作都从详情页进入，保存前显示余额影响；不能只靠列表左滑暴露危险删除操作。

### 9.5 多币种 UI

- 金额输入先选原币种，默认最近使用币种；内置计算器在同一键盘区域使用。
- 非账本基准币时，金额下方显示“1 原币 = X 基准币”、汇率日期和来源。
- 使用 72 小时内缓存汇率时显示“离线汇率”；超过期限必须要求用户确认或手动输入。
- 明细行以原币金额为主、基准币折算为辅；余额与结算始终以账本基准币为主。
- 用户修改汇率、币种或原币金额时，保存前展示每位受影响者的余额变化。
- 不支持小数的币种不能出现虚假的 `.00`；三位小数币种必须完整展示其合法精度。

## 11. 布局与视觉规格

### 11.1 间距和尺寸

- 手机页面左右安全边距沿用当前详情页，目标为约 16 px。
- 卡片内部间距以 12/16 px 为主，信息行间距使用 8 px。
- 工具条四项等宽，每项有效点击区域不小于 44×44 px。
- 头像默认 28–32 px，重叠时保留 2 px 暖白描边。
- 主卡圆角沿用当前封面/公告体系，不创造超大悬浮玻璃卡。
- 金额列预留足够宽度，长币种和大额数字不能挤压状态文字。

### 11.2 字体层级

复用 Friemi 当前字体，不为核算模块额外加载金融风格字体。

| 内容 | 建议层级 |
| --- | --- |
| 聚吧标题 | 保持当前最大标题层级 |
| 核算页标题 | 页面二级标题 |
| 个人应付/应收金额 | 核算模块最大数字，使用等宽数字特性 |
| 总支出 | 次于个人金额 |
| 卡片标题/成员名 | 中等强调 |
| 日期、提交人、参与人数 | 次级正文 |
| 状态标签 | 小号但必须满足可读性 |

### 11.3 色彩规则

- 深绿：当前模块、主操作、正常应收和已结清。
- 珊瑚色：争议、驳回、作废和危险操作；不能用来表达普通欠款羞辱感。
- 暖黄色/米色：待确认、预计、同步中。
- 淡蓝：纯信息提示，例如汇率说明。
- 黑色：金额与正文。
- 次级灰：元数据和未激活工具。

“需付款”使用中性正文色加明确文字，不把欠款人整行染红。

### 11.4 图标规则

- 线性、圆角端点、视觉重量与当前聚吧元数据图标一致。
- 聊天使用对话气泡；详情使用信息卡；公告使用铃铛/公告板；核算使用账单、钱包或计算勾选组合。
- “核算”图标不能使用银行大楼、硬币堆或投资图表，避免产品被误解为金融账户。
- 费用分类使用食物、场地、交通、票务、其他等友好图形，不使用复杂彩色插画充当操作图标。

### 11.5 图片与插画

- 当前聚吧封面图保持页面第一视觉资产。
- 旧稿的大幅 AA 人物插画只适合首次使用说明或空状态，不放进每次核算页面。
- 收据照片属于单笔费用附件，不在聚吧工具条建立独立“照片”模块。
- 如后续制作 AA 空状态插画，应继续使用 Friemi 现有插画比例、肤色多样性和绿色主色，不直接复制旧稿素材。

### 11.6 动效

- 页面切换、页签和卡片展开使用 180–240 ms 的轻量动效。
- 付款确认可使用一次短促勾选反馈，但不使用金币飞舞、余额滚动博彩化效果。
- 结算建议失效、金额变化和争议必须立即静态展示，不能用动画掩盖数据更新。
- 尊重系统“减少动态效果”设置。

## 12. 不同身份看到什么

### 12.1 未报名访问者

- 看得到“核算”入口，点击后显示“报名后可查看本次活动核算”。
- 看不到总支出、个人余额、付款状态、收款方式和收据。
- 不使用灰色整卡泄露“有几个人欠款”等信息。

### 12.2 普通参与者

- 默认看到自己的应付/应收和与自己有关的下一步。
- 可查看全组已入账明细与结算透明度。
- 可提交自己的费用，并查看审核状态。
- 不能确认别人的费用或修改主理人设置。

### 12.3 主理人

- 默认摘要增加待确认费用、待确认收款和争议数量。
- 可以冻结记录、开启结算、提醒未完成成员和归档。
- 主理人仍然是普通账务参与者，不因角色自动免除或增加分摊。
- 不能通过 AA 增加组织费、服务费或利润；这些商业收费若存在，必须由其他明确产品能力承载。

### 12.4 游客

- 游客没有 Friemi 账户时由主理人代录，或通过只访问该聚吧的专属链接查看/确认。
- 游客的余额、付款和历史保留在稳定参与者 ID 下，注册后认领。
- 同一个游客不能因重复添加而出现两个债务身份；合并前必须预览金额。

## 13. 核算状态在详情页如何表现

工具条“核算”入口只展示一个轻量角标，详情页不直接堆放完整财务卡。

| 核算状态 | 工具条表现 | 点击后的首要内容 |
| --- | --- | --- |
| 未启用/空账本 | 无角标 | 功能说明与“记第一笔” |
| 有待审核费用 | 数量角标 | 主理人进入待确认列表；参与者看到提交状态 |
| 记录中 | 轻点或无角标 | 预计余额和明细 |
| 待付款 | 当前用户有行动时显示数量 | 自己的付款路径 |
| 待确认收款 | 数量角标 | 待确认转账 |
| 有争议 | 珊瑚色小点加文字提示 | 争议详情 |
| 已结清 | 小勾或无角标 | 结算完成摘要 |
| 离线/数据过期 | 不伪造金额角标 | 最后同步时间和重试入口 |

### 13.1 角标计数规则

- `聊天` 显示未读消息数，超过 99 显示 `99+`。
- `公告` 只显示未读圆点，不用数量与聊天竞争。
- `核算` 只统计当前用户需要亲自处理的事项，超过 9 显示 `9+`。
- 主理人的核算待办包括待审费用、待确认收款和待处理争议；参与者的核算待办包括需付款、需确认收款、被驳回后待修改和与自己有关的争议。
- “有人新增了一笔已计入费用”属于通知，不计入长期角标；用户查看后即消除未读状态。
- 同一对象同时命中多个条件时只计一次，全部解决后角标必须归零。

### 13.2 加载、空态与错误态

| 状态 | UI 规则 |
| --- | --- |
| 首次加载 | 使用与真实卡片同结构的骨架，不先显示 `¥0.00` 或“已结清” |
| 空账本 | 显示一句说明和“记第一笔”；不展示空图表与六个空统计卡 |
| 使用缓存 | 顶部显示“更新于 HH:mm”，金额可查看但结算前必须刷新 |
| 完全离线 | 已授权用户可保存待同步费用；不能开启结算、确认审核或确认收款 |
| 同步失败 | 保留用户输入，显示重试和错误说明，不复制生成第二笔 |
| 无权限 | 不渲染缓存金额，提供返回聚吧详情的出口 |
| 对象已作废 | 展示作废状态、操作者与时间，有权限者可进入恢复流程 |
| 服务维护 | 显示维护窗口与只读范围，不把按钮点击伪装成成功 |
| 账务不变量失败 | 隐藏结算操作，显示“数据核对中”，上报严重错误并阻止付款确认 |

## 14. 内容与术语

### 14.1 命名层级

- 聚吧工具入口：`核算`
- 二级页面标题：`AA 核算` 或简写 `核算`
- 记录动作：`记一笔`
- 费用审核：`待主理人确认 / 已计入 / 已驳回`
- 金额状态：`你需付 / 你应收 / 你已结清`
- 付款阶段：`待付款 / 已付款·待确认 / 已结清 / 有争议`
- 全局计算动作：`重新核算`

“核算”表示汇总并计算，“结算”表示实际付款收尾。二者不能在按钮和状态中混用。

### 14.2 推荐文案

| 场景 | 文案 |
| --- | --- |
| 免费活动首次进入 | “免费表示没有报名费；共同产生的实际开支仍可在这里 AA。” |
| 空账本 | “还没有共同开支。有人先垫钱时，在这里记一笔。” |
| 非均分 | “每个人承担的金额不同，请确认你的分摊。” |
| 付款说明 | “款项直接转给参与者，Friemi 不经手资金。” |
| 结算对象陌生 | “系统合并了全组余额，让大家少转几笔。” |
| 修改旧费用 | “这会改变 4 位参与者的余额，并重新生成付款路径。” |
| 提醒未付款 | “提醒未结清成员” |

避免使用“催债”“欠钱不还”“强制付款”“平台代收”等表达。

## 15. 活动成本政策如何进入 UI

旧稿强调 AA 只能覆盖真实活动成本，主理人不能借 AA 获利。迁移到 Friemi 后规则如下：

- AA 费用必须对应聚吧直接发生的共同成本。
- 已入账支出合计决定可分摊总额，参与者付款总额不能高于结算算法要求。
- 主理人垫付可以正常收回，但不能把组织时间、劳动或利润伪装成支出。
- 组织费、报名费或平台服务费必须在聚吧收费体系中单独标示，不能混进 AA 明细。
- 后续退款、折扣返还和押金退回应记录为 Income，重新降低净成本。
- 所有参与者都可以查看费用来源和变更记录；对可疑费用可发起争议。

UI 不使用“Friemi 认证开支”等暗示，除非平台确实完成了凭证审核。

## 16. 隐私与安全体验

- 未报名访问者不能通过核算入口看到金额和成员关系。
- 收款方式只在真实结算关系中按需展示，默认遮罩敏感部分。
- “复制成功”使用短提示，不在剪贴板写入多余的活动信息。
- 收据可能包含地址、卡号尾号和姓名，上传前提示用户检查敏感内容。
- 截图分享结算摘要时默认只包含昵称和状态，不包含完整付款账号。
- 主理人修改成员费用、确认转账或处理争议都必须留下活动记录。
- 详情页只显示待处理数量，不在公共区域显示具体欠款金额。

## 17. 响应式与无障碍

- 以当前 365 px 左右的移动详情页为基准，320–430 px 范围内不产生横向滚动。
- 四项工具条保持单行四等分；长语言优先缩短文案，不缩小到不可读字号。
- 大屏仍保持社交内容宽度，不扩展成密集财务仪表盘；核算中心可在宽屏使用摘要与列表双栏。
- 所有金额带币种，屏幕阅读器需要读出“你需付人民币六十二元”，而不是只读数字。
- 状态不能仅靠颜色；图标、文字和可访问标签同时存在。
- 点击区域至少 44×44 px，支持系统字体缩放和减少动态效果。
- 长昵称、emoji、无小数币种、大额金额和混合中英文必须进入视觉回归测试。

## 19. 两份 MD 的后续融合规则

本阶段保留两份独立文档：

1. `aa-billing-product-logic.md`：平台无关的账务、权限、状态和计算逻辑。
2. `friemi-aa-ui-integration.md`：Friemi 聚吧中的入口、角色适配、审核层和 UI 语言。

后续融合时建议生成：

friemi-aa-product-spec.md

├── 聚吧身份/状态到 AA 领域的映射

## 20. 完整性结论

旧 AA 概念稿中的进入活动、总览、上传开支、确认分摊、付款路径和结算进度均已获得明确的新 UI 归属；当前 Friemi 详情页中的封面、元数据、公告、发起人、参与者、群聊和主理人操作也都完成了保留、合并或去重。

最终确定：

- AA 功能以“核算”进入聚吧详情页。
- 工具条固定为“聊天、详情、公告、核算”。
- “公告”替换旧工具条中的“照片”，不替换聚吧封面。
- 原“已报名”与工具条合并，原底部“群聊”按钮去重。
- 旧六页压缩为核算中心和任务页，不保留独立 Settlement 产品壳。
- 聚吧报名、主理人、游客和生命周期自动映射到 AA 账本。
- 一个聚吧只对应一个有效账本；所有权移交、活动复制、取消和删除都有不会丢账的规则。
- Friemi 默认使用费用审核和转账双向确认，核心金额逻辑保持不变。
- 审核层与核心交易层已经分离，组合 UI 状态统一派生，不会形成第二套余额算法。
- 导航返回、通知深链、离线缓存、权限失败和服务维护都有明确出口。
- Friemi 的 UI、图标、框架、布局和状态语言是最终视觉来源，Tricount 只提供功能启发，不提供视觉资产。

因此，本方案的页面、身份、状态、数据和异常路径均已闭环，已经可以作为后续两份 MD 融合、线框设计和前端实现的 UI 基准，也可以安全地作为 `Event` 领域下的可配置模块进行适应性嵌套。

适应性嵌套的正式边界为：

- 宿主聚吧负责上下文、报名身份、主理人权限、聊天、公告和活动生命周期。
- Friemi 适配层负责成员同步、费用审核、页面组合状态和入口角标。
- AA 核心负责交易、金额、分摊、余额、汇率和结算，宿主不得自行重算。
- 支付与通知通过适配接口接入，失败不会改变核心账务事实。

在此边界内替换客户端框架、页面容器、图标实现、汇率服务、通知渠道或支付跳转方式，都不需要修改核心 AA 算法。父子聚吧跨账本汇总、跨活动统一结算和真实资金托管不在当前嵌套边界内；若以后提出，应作为新范围设计，而不是在现有页面中隐式增加。
