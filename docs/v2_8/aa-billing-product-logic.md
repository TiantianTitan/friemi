# AA 计费器 v2.8：产品拆解与核心逻辑

> 文档状态：产品逻辑定稿（Final）
> 更新日期：2026-09-11
> 参考对象：Tricount 当前公开产品、官网功能页与帮助中心
> 目标：不复制品牌、文案或视觉资产，在公开可观察能力的基础上，设计一套功能完整、计算可信、适合中文用户的多人 AA 记账产品。

## 0. 结论先行

本产品不是“把一笔账除以人数”的计算器，而是一个多人共享账本：持续记录谁付了钱、哪些人参与消费、每个人应该承担多少，并随时给出当前净余额与可执行的结算方案。

核心账务恒等式为：

```text
个人净余额 = 累计垫付 + 应得收入份额 + 已付还款
           - 累计消费份额 - 实际收到的公共收入 - 已收还款
```

- 净余额 `> 0`：此人应收款。
- 净余额 `< 0`：此人应付款。
- 净余额 `= 0`：此人已结清。
- 所有参与者净余额之和必须始终为 `0`。

v2.8 的核心体验目标是：10 秒内记完一笔账；任何金额都能解释来源；多人同时操作不重复记账；离线记录不丢失；结算建议清楚说明“为什么要付给这个人”。

## 1. 拆解范围与事实边界

### 1.1 标记约定

- **[公开]**：Tricount 官网、帮助中心或应用商店明确展示的行为。
- **[可观察]**：可通过公开客户端操作验证，但不代表其内部实现方式。
- **[本产品]**：为 AA 计费器独立制定的产品规则。
- **[验证项]**：产品规则已经确定，但仍需通过实现测试或可用性测试验证结果。

### 1.2 Tricount 的公开产品骨架

根据官方公开资料，可以确认其核心产品结构如下：

1. **共享账本**：创建一个 tricount，添加参与者，通过链接邀请，参与者可以共同添加支出并查看余额。
2. **三类账务记录**：支出（Expense）、转账/还款（Transfer）、收入（Income）。
3. **灵活分摊**：支持均分、不均分、按份数或直接输入个人金额。
4. **余额与结算**：先计算每个人多付或少付多少，再生成减少转账笔数的还款建议；因此可能建议把钱付给一个没有直接替自己垫付过的人。
5. **金额精度**：官方说明精确到最小货币单位，例如 EUR 为 `0.01`；无法整除时由其中一人承担余下的 1 分。
6. **多币种**：账本有默认币种，单笔支出可使用其他币种，系统按汇率折算，并以账本默认币种给出结算建议。
7. **协作与同步**：参与者可查看最新记录；支持服务端同步、手动刷新与离线新增后自动同步。
8. **辅助能力**：收据照片、计算器、支出统计、付款请求、归档/恢复、Splitwise 导入等。
9. **参与者生命周期**：公开帮助说明单账本最多 50 人；被移除但仍有历史账务的人需要保留结算能力，不能继续新增支出。

## 2. 产品定位

### 2.1 一句话定义

一个面向朋友出行、聚餐、情侣和合租场景的移动优先共享账本，让任何人都能快速记账，并用可解释的方式完成公平结算。

### 2.2 默认目标用户假设

在没有更具体用户画像之前，v2.8 默认服务以下中文用户：

- 2–12 人的小型旅行、聚餐、活动群体。
- 长期共同支出的情侣、家庭和室友。
- 使用 CNY 为主，也会在境外旅行中使用多币种的人。
- 不愿学习会计术语，希望通过分享链接或二维码直接加入的人。
- 实际付款主要发生在微信、支付宝、银行卡或现金中，产品本身暂不托管资金。

### 2.3 用户真正要完成的任务

1. 我先垫了钱，马上记下来，之后不用再回忆。
2. 这笔钱不是所有人均摊，我能快速选人和修改比例。
3. 我想知道自己现在是欠钱还是应收，而不是读懂一张会计表。
4. 活动结束后，我希望尽量少转几笔就结清。
5. 有人改错或删错账时，我能看见发生了什么并恢复。
6. 没有网络时照常记录，联网后也不会重复生成两笔。

### 2.4 设计原则

- **先记下来，再完善**：新增记录只要求金额、付款人、参与人和分摊方式，其余字段可选。
- **每个数字可解释**：余额、总额和结算建议均可下钻到来源记录。
- **钱只用整数算**：内部一律使用货币最小单位，不使用二进制浮点数。
- **协作默认开放，修改必须留痕**：降低群体记账摩擦，同时保留完整活动记录。
- **建议不等于付款**：生成或发送付款请求不改变余额；只有确认的转账记录才能改变余额。
- **历史不随外部数据漂移**：汇率一旦随交易保存，后续行情变化不能改写旧账。

### 2.5 v2.8 非目标

- 不提供银行卡、信用卡、余额账户或资金托管。
- 不承诺微信/支付宝到账状态，除非未来接入正式支付回调。
- 不包含 eSIM、信贷或银行开户等与 AA 核心无关的金融能力。
- 不复制 Tricount 的品牌、名称、图标、文案、页面布局或其他受保护资产。

## 4. 核心领域模型

### 4.1 账户与参与者必须分离

`User` 表示真实登录账户；`Participant` 表示某个账本中的记账身份。两者不能混为一体。

这样可以支持：

- 创建者先用昵称添加“阿明”，阿明之后再通过邀请链接认领该身份。
- 未注册访客先参与，之后登录也不会丢失历史。
- 同一用户在不同账本中使用不同昵称。
- 成员离开后保留历史账务，但不继续获得编辑权限。

### 4.2 主要对象

| 对象 | 核心字段 | 关键规则 |
| --- | --- | --- |
| `User` | `id`、登录凭据、语言、时区 | 不直接参与金额计算 |
| `Ledger` | `id`、名称、图标、默认币种、时区、状态、创建者 | 无交易时可改默认币种；有交易后必须显式迁移 |
| `Participant` | `id`、`ledger_id`、昵称、绑定账户、角色、状态 | 使用稳定 ID；改名不能改变历史金额 |
| `Transaction` | `id`、类型、标题、日期、原币金额、基准币金额、汇率快照、分类、备注、附件、版本 | 类型为 `EXPENSE`、`INCOME` 或 `TRANSFER` |
| `Contribution` | 交易 ID、参与者 ID、实付/实收金额 | 支持一人或多人付款/收款 |
| `Allocation` | 交易 ID、参与者 ID、应承担/应得金额、分摊模式、输入值 | 保存最终落到最小货币单位的结果 |
| `Category` | 账本 ID、名称、图标、排序、状态 | 预置分类与账本自定义分类并存；停用不改历史 |
| `Attachment` | 交易 ID、类型、私有对象键、上传状态、创建者 | 独立上传和重试；失败不能回滚账务 |
| `SettlementSuggestion` | 付款人、收款人、建议金额、计算版本 | 派生数据，不是账务记录 |
| `PaymentRequest` | 建议 ID、发送者、接收者、金额、渠道、状态 | 只是沟通记录，永不直接改变余额 |
| `Invite` | token、账本、默认角色、有效期、状态 | 可撤销、可轮换、不可被顺序猜测 |
| `Activity` | 操作者、动作、对象、前后版本、时间 | 用于审计、冲突解释和恢复 |

### 4.3 状态模型

**账本状态**

```text
ACTIVE <──> FROZEN ──> ARCHIVED <──> ACTIVE（恢复）
   │           │            │
   └───────────┴────────────┴──> DELETION_PENDING -> DELETED
                                      │
                                      └──> 删除前状态（30 天内恢复）
```

- `ACTIVE`：允许按权限新增和修改。
- `FROZEN`：只允许结算和管理员解冻，适合活动结束后对账。
- `ARCHIVED`：默认只读并从首页隐藏；恢复后回到 `ACTIVE`。
- `DELETION_PENDING`：30 天冷静期内全员只读并显示删除日期；Owner 可恢复到删除前状态。
- `DELETED`：冷静期结束后的终态，业务数据按保留政策清除，不允许从客户端恢复。
- “全部结清”是计算状态，不自动归档。

**成员状态**

```text
INVITED -> ACTIVE -> INACTIVE
```

- 有历史账务的参与者只能停用，不能物理删除。
- 停用成员仍出现在历史明细和未结余额中，但不能新增记录。
- 无任何引用的占位参与者才允许彻底删除。

**交易状态**

```text
DRAFT -> PENDING_SYNC ────────────────> POSTED <-> VOIDED
                     └-> PENDING_CONFIRMATION -> POSTED
                                                └-> DISPUTED -> POSTED / VOIDED
```

- 修改产生新版本，不能静默覆盖旧值。
- 删除实际是 `VOIDED`，默认不参与计算，可由有权限的人恢复。
- 离线创建先进入 `PENDING_SYNC`，同步成功后进入 `POSTED`。
- 普通支出和收入不经过 `PENDING_CONFIRMATION`；它只用于开启“双向确认”的转账。
- `DISPUTED` 只用于转账争议；争议期间该转账暂不参与余额，解决后恢复入账或作废。

**邀请状态**

```text
ACTIVE -> EXPIRED / REVOKED / EXHAUSTED
```

- `EXPIRED`：超过有效期；`REVOKED`：管理员主动撤销；`EXHAUSTED`：达到加入次数上限。
- 三种终止状态都不得继续读取账本信息，也不能通过刷新 token 恢复。

**付款请求状态**

```text
CREATED -> SENT -> OPENED -> RESOLVED
                  └──────> CANCELLED / EXPIRED

RESOLVED -> OPENED（关联转账被争议或作废）
```

- 只有关联到有效 `POSTED` 转账时才进入 `RESOLVED`。
- `OPENED`、`CANCELLED`、`EXPIRED` 都不改变余额，且不能被显示成已付款。
- 已解决请求关联的转账被争议或作废时，请求重新进入 `OPENED` 并标记“付款待核对”。

### 4.4 账户生命周期

```text
GUEST -> ACTIVE -> LOCKED -> ACTIVE
                    └────> DELETION_PENDING -> ANONYMIZED
```

- `GUEST`：凭邀请 token 使用单个账本，不拥有跨设备恢复能力。
- `ACTIVE`：至少绑定并验证一种登录方式；可管理多个账本和设备会话。
- `LOCKED`：登录风险、用户主动锁定或验证失败时暂停写入，但不删除账务。
- `DELETION_PENDING`：账户进入 30 天冷静期；用户可撤销删除。
- `ANONYMIZED`：冷静期结束后删除账户身份数据；共享账本的必要账务记录改为匿名参与者，不能破坏其他成员的历史余额。

安全敏感操作（移交所有权、删除账本、导出完整数据、修改登录方式）必须重新验证身份。用户可以查看并撤销其他设备会话。

账户进入 `DELETION_PENDING` 前必须先移交仍在使用账本的所有权，或同时删除仅自己使用的账本；系统不能留下无 Owner 的协作账本。账户恢复依赖已验证登录方式和恢复流程，不允许客服仅凭昵称或账本金额重置访问权。

## 5. 金额与精度

### 5.1 存储规则

所有账务金额使用整数最小货币单位：

- CNY `¥10.01` 存为 `1001` 分。
- JPY `¥100` 存为 `100` 日元。
- 支持三位小数的币种按其 ISO 4217 指数处理。
- 汇率使用高精度十进制定点数或 Decimal 类型，禁止使用 `float` / `double` 直接参与结算。

数据库中的金额字段必须同时带币种，禁止只有裸数字。

### 5.2 通用账务不变量

任何已入账交易都必须满足：

```text
支出：Σ实付金额 = 交易总额 = Σ应承担金额
收入：Σ实际收款 = 交易总额 = Σ应得金额
转账：Σ余额变化 = 0
账本：Σ所有参与者净余额 = 0
```

如任一等式不成立，交易不得进入 `POSTED`。

### 5.3 金额输入

- 金额必须大于 `0`；零金额只能保留为草稿。
- 负数不用于表达退款；退款应记录为“收入”。
- 输入框支持 `+ - × ÷ ( )` 的简单计算，但保存前只保留最终金额。
- 粘贴带货币符号或千位分隔符的数字时应自动清洗，并在保存前回显标准格式。
- 超大金额、超过币种精度的金额和非法表达式必须就地报错。

### 5.4 日期、时区与排序

- `occurred_on` 表示交易归属日期，按账本时区解释；`created_at`、`updated_at` 为 UTC 审计时间。
- 用户可以记录未来日期的已发生付款，例如提前购买下月车票。只要交易为 `POSTED`，它立即影响当前余额，不等同于周期任务或待执行预算。
- 未来日期交易显示“未来”标记，并在保存前二次确认，避免误选年份。
- 统计按 `occurred_on` 归入对应日/月/年；默认统计可包含未来记录，但必须提供“排除未来记录”开关并显示未来金额小计。
- 明细默认按 `occurred_on` 倒序，再按 `created_at` 倒序，最后按稳定交易 ID 排序；离线同步后不得随机换序。
- 修改账本时区不改变已经保存的 `occurred_on`，只影响之后的默认日期和日界线。
- 周期性账单属于 P2；不得通过自动复制未来交易的方式隐式实现。

## 6. 三种账务类型

### 6.1 支出 Expense

含义：一名或多名参与者替自己、全组或部分成员支付了费用。

对参与者 `i`：

```text
支出余额变化 ΔBᵢ = paidᵢ - owedᵢ
```

- `paidᵢ`：此人实际垫付。
- `owedᵢ`：此人应承担的消费份额。
- 付款人可以不在消费参与人中，例如家长替一群人付款。
- v2.8 支持多付款人；常规入口默认单付款人，避免增加操作复杂度。

### 6.2 收入 Income

含义：一名或多名参与者收到了属于全组或部分成员的公共收入，例如退款、返现、押金退回或共同物品出售所得。

对参与者 `i`：

```text
收入余额变化 ΔBᵢ = entitledᵢ - receivedᵢ
```

- `entitledᵢ`：此人应得的收入份额。
- `receivedᵢ`：此人实际收到的现金。
- 收到公共收入的人持有了别人的份额，因此其余额可能下降。
- 收入使用与支出相同的均分、权重、百分比和自定义金额规则，只是界面把“应承担”改写为“应得”。
- 收入单独统计，不用负支出伪造。

### 6.3 转账 Transfer

含义：参与者之间已经实际发生的还款或资金转移。

当 A 向 B 支付 `x`：

```text
ΔB_A = +x
ΔB_B = -x
```

如果 A 原本欠款，付款会使 A 的负余额向 0 靠近；B 收到钱后，其正余额向 0 靠近。

以下动作必须分开：

- “生成结算建议”：不改变余额。
- “发送付款请求”：不改变余额。
- “复制金额/备注或打开支付应用”：不改变余额。
- “标记已付款并生成转账记录”：改变余额。
- 接入支付平台后收到可信到账回调：自动确认转账并改变余额。

## 7. 分摊规则

### 7.1 均分

用户选择参与消费的人，系统把总额平均分配。

```text
raw_share = total_minor / participant_count
```

无法整除时，用“最大余数法”分配剩余最小货币单位。均分场景中各人的小数余数相同，因此使用交易 ID 与参与者 ID 生成稳定排序，避免永远由列表第一人承担余数。最终结果写入 `Allocation`，之后不因成员排序或改名而变化。

示例：`¥100.00 / 3` 最终必须是 `¥33.34 + ¥33.33 + ¥33.33`，且界面提示“因无法整除，有 1 人多承担 ¥0.01”。

### 7.2 按份数/权重

用户为每人输入份数，例如 `2 : 1 : 1`。

```text
raw_shareᵢ = total_minor × weightᵢ / Σweight
```

- 权重必须 `>= 0`，总权重必须 `> 0`。
- 权重为 `0` 等于不参与，但界面应直接显示“未参与”。
- 先取整数部分，再按小数余数从大到小分配剩余单位；完全相同的余数使用稳定排序。

### 7.3 按百分比

百分比本质上是权重的友好输入方式。

- 总百分比必须为 `100%`。
- 可允许最多四位小数输入，最终仍以最小货币单位结算。
- 系统显示“还差 X%”或“已超出 X%”，不能悄悄归一化用户输入。

### 7.4 自定义金额

用户直接输入每个人承担的准确金额。

- 输入总和必须等于交易总额。
- 编辑过程中持续显示“还剩 ¥X 待分配”或“超出 ¥X”。
- 提供“把剩余金额给某人”和“均分剩余金额”的快捷操作。
- 不自动修改用户已输入的个人金额。

### 7.5 按项目分摊

逐项点单、税费和小费拆分是增强能力，不是 v2.8 首发阻塞项。数据模型应预留 `LineItem`：

- 每个项目有名称、数量、金额和参与者。
- 税费、服务费、折扣可按项目金额比例或自定义规则二次分摊。
- 所有项目与调整项之和必须回到账单总额。

## 8. 余额计算

### 8.1 唯一可信来源

余额是所有有效交易推导出来的结果，不允许作为可编辑字段单独维护。

```text
Bᵢ = ΣExpense(paidᵢ - owedᵢ)
   + ΣIncome(entitledᵢ - receivedᵢ)
   + ΣTransfer(sentᵢ - received_transferᵢ)
```

实现可以缓存余额，但缓存必须带 `ledger_version`；版本不一致时重新计算。

### 8.2 展示语义

禁止只显示 `+¥80`、`-¥80` 而不解释含义。统一使用：

- “你应收 ¥80.00”
- “你需付 ¥80.00”
- “你已结清”

成员列表中同时使用颜色、图标和文字，不能只依赖红绿区分。

### 8.3 总额定义

为避免“总额到底包不包含还款”的歧义，固定展示以下指标：

| 指标 | 定义 | 是否包含转账 |
| --- | --- | --- |
| 总支出 | 所有有效 Expense 的基准币金额 | 否 |
| 总收入 | 所有有效 Income 的基准币金额 | 否 |
| 净成本 | 总支出 - 总收入 | 否 |
| 我垫付 | 我的 Expense 实付合计 | 否 |
| 我消费 | 我的 Expense 应承担合计 | 否 |
| 我的净余额 | 按完整余额公式计算 | 是 |

所有统计页面都必须写出指标名称，不能用一个模糊的“我的总计”。

## 9. 推荐结算算法

### 9.1 目标

默认目标是生成金额正确、笔数较少、结果稳定且容易解释的还款方案。

结算建议基于全局净余额，而不是要求每个欠款人逐笔还给原始付款人。因此，一个人可能需要付款给没有直接替自己垫付过的人。界面必须提供“为什么付给 TA”的解释。

### 9.2 确定性贪心方案

1. 取所有正余额参与者作为债权人。
2. 取所有负余额参与者作为债务人。
3. 分别按绝对金额从大到小排序；金额相同按稳定参与者 ID 排序。
4. 最大债务人与最大债权人匹配，金额为两者余额绝对值的较小值。
5. 更新临时余额；任一方归零后移动到下一人。
6. 直到所有余额为零。

伪代码：

```text
while debtors not empty and creditors not empty:
    debtor = debtors.first
    creditor = creditors.first
    amount = min(abs(debtor.balance), creditor.balance)
    suggest debtor -> creditor: amount
    debtor.balance += amount
    creditor.balance -= amount
    remove every zero balance entry
```

该方法：

- 保证金额正确。
- 最多产生“非零余额人数 - 1”笔转账。
- 对相同输入总是产生相同结果。
- 不宣称在所有情况下得到数学意义上的全局最少笔数。

若未来必须追求严格最少笔数，可在非零人数较少时增加分支限界算法；大群组仍使用确定性贪心，避免指数级延迟。

### 9.3 建议版本与失效

- `SettlementSuggestion` 绑定当前 `ledger_version`。
- 任一支出、收入或转账发生新增、修改、作废后，旧建议立即标记过期并重新计算。
- 用户不能把“旧建议中的金额”直接确认成当前还款，除非再次核对余额。
- 当差额为最小货币单位的 `0` 时才显示“全部结清”。

### 9.4 可解释性

点击某条结算建议时显示：

```text
你当前少付 ¥145.00
小明当前多付 ¥180.00
系统合并全组债务后，建议你向小明支付 ¥135.00，
这样可以减少大家需要操作的转账笔数。
```

同时提供“查看影响我余额的明细”，让用户检查原始交易，而不是把算法描述成不可质疑的黑盒。

## 10. 多币种

### 10.1 基本规则

- 每个账本有一个 `base_currency`，所有余额和结算建议以它为准。
- 每笔交易保留 `original_currency`、`original_amount`、`fx_rate`、`base_amount`、汇率来源和抓取时间。
- 汇率方向在数据契约中固定为：

```text
base_amount = original_amount × fx_rate
```

- 自动汇率只是建议，用户可在保存前或编辑时手动覆盖。
- 历史汇率快照不可被新的市场汇率自动改写。

### 10.2 换算与分摊顺序

1. 在原币种中校验交易总额和用户输入。
2. 用交易汇率得到基准币总额，只舍入一次到基准币最小单位。
3. 按分摊规则计算各人的基准币份额。
4. 使用最大余数法保证所有基准币份额之和严格等于基准币总额。
5. 同时保存原币展示值与最终基准币分摊结果。

不得对每个人独立换算后简单相加，否则会产生无法解释的汇兑尾差。

### 10.3 修改默认币种

修改账本默认币种时采用“从此刻起生效”：

- 旧交易保留原基准币及汇率，不批量重估。
- 为避免一个账本出现两套不可相加的基准余额，v2.8 默认只允许在账本没有已入账交易时修改默认币种。
- 已有交易后如需更换，推荐复制为新账本或执行一次显式迁移；迁移前必须预览全部汇兑差额并由管理员确认。

### 10.4 跨币种还款

建议金额始终先以账本基准币生成。用户选择用其他币种实际还款时：

- 输入实际付款币种、金额和汇率。
- 明确显示这笔还款抵扣多少基准币余额。
- 若存在尾差，保留未结余额，不自动标记全部结清。

## 11. 完整示例

账本成员为 A、B、C，默认币种 CNY。

### 11.1 支出一：晚餐

- 总额：`¥300`
- A 付款：`¥300`
- A、B、C 均分：每人 `¥100`

余额变化：

| 成员 | 实付 | 应承担 | 余额变化 |
| --- | ---: | ---: | ---: |
| A | 300 | 100 | +200 |
| B | 0 | 100 | -100 |
| C | 0 | 100 | -100 |

### 11.2 支出二：出租车

- 总额：`¥90`
- B 付款：`¥90`
- 只有 B、C 参与：各 `¥45`

余额变化为 B `+45`、C `-45`。累计余额：A `+200`、B `-55`、C `-145`。

### 11.3 收入：商家退款

- A 实际收到退款：`¥30`
- A、B、C 均分退款权益：各 `¥10`

余额变化：A `10 - 30 = -20`；B `+10`；C `+10`。

最终余额：

| 成员 | 净余额 | 语义 |
| --- | ---: | --- |
| A | +180 | 应收 ¥180 |
| B | -45 | 需付 ¥45 |
| C | -135 | 需付 ¥135 |

推荐结算：B 向 A 支付 `¥45`，C 向 A 支付 `¥135`。两笔转账确认后，三人余额都变为 `0`。

## 12. 协作、身份与权限

### 12.1 角色矩阵

| 能力 | Owner | Admin | Member | Viewer |
| --- | :---: | :---: | :---: | :---: |
| 查看账本与余额 | ✓ | ✓ | ✓ | ✓ |
| 新增自己的记录 | ✓ | ✓ | ✓ | — |
| 修改/作废自己的记录 | ✓ | ✓ | ✓ | — |
| 修改/作废他人记录 | ✓ | ✓ | 按账本设置 | — |
| 邀请普通成员 | ✓ | ✓ | 按账本设置 | — |
| 管理成员与角色 | ✓ | ✓ | — | — |
| 冻结、归档、恢复账本 | ✓ | ✓ | — | — |
| 删除账本/移交所有权 | ✓ | — | — | — |

默认使用“开放协作”：Member 可以新增记录，但修改他人记录需要管理员权限。旅行群可由 Owner 开启“成员可共同纠错”。

交易的“归属”按 `created_by` 判断，不按付款人判断。Member 可以记录“由另一名活跃参与者付款”的支出，但该付款人必须收到通知；普通 Member 不能创建发生在另外两人之间、与自己无关的转账，Owner/Admin 可以代录并通知双方。任何代录行为都必须在活动记录中显示创建者。

### 12.2 无账号加入

- 用户可以先在本机创建和体验未分享账本；首次生成邀请、启用跨设备同步或执行完整导出前，创建者必须升级为已验证账户，以保证账本存在可恢复的 Owner。
- 分享链接或二维码只授予单个账本的受限访问，不等于完整账户会话。
- 邀请分为“可编辑”和“只读”；可编辑 Guest 能新增、修改和作废自己创建的记录，但不能修改他人记录或管理账本。
- Guest 的 token 失效后，已入账记录继续保留；未登录前不能再写入，只能申请新邀请或升级账户。
- 首次进入时用户必须选择“我是已有成员”或“新增我自己”。
- 认领已有身份需要管理员确认，或由创建者预先生成一人一链接。
- 一个参与者身份同一时间只能绑定一个有效账户；合并身份必须先预览余额影响。
- 需要跨设备恢复、接收推送或管理多个账本时再引导注册，不阻塞首次体验。

### 12.3 邀请安全

- token 使用足够长度的随机值，不在 URL 中包含成员姓名或账本金额。
- Owner/Admin 可以撤销、轮换、限制有效期和限制加入次数。
- 账本被冻结或归档后，邀请链接默认暂停。
- 涉及金额的推送和链接预览默认隐藏具体数值，用户可自行开启。

### 12.4 成员删除与退出

- 被交易引用或余额非零的成员不可硬删除，只能停用。
- 停用成员仍可查看与确认自己的结算，但不能新增支出。
- 余额归零且无待确认转账后可以退出；历史记录仍显示当时身份。
- Owner 退出前必须移交所有权。
- 同一账户不能同时绑定同一账本中的两个参与者身份。出现重复身份时，Owner/Admin 可执行合并：先预览余额和受影响记录，再把来源 ID 的 Contribution/Allocation 归并到目标 ID；同一交易中的金额相加，账务不变量保持不变，来源身份转为不可再使用的别名。
- 成员合并必须留下可恢复的活动记录；恢复时若会与之后的新交易冲突，需先冻结账本并由管理员处理。

## 13. 新增与编辑流程

### 13.1 快速记一笔

默认表单顺序：

1. 金额与币种。
2. 谁付了。
3. 哪些人参与。
4. 怎么分。
5. 标题。
6. 可选：日期、分类、备注、照片。

体验规则：

- 默认付款人为当前用户在该账本中的参与者身份。
- 默认参与人为上一次使用的组合；首次使用默认全员。
- 默认分摊方式为上一次方式；界面始终展示分摊后的个人预览。
- 交易币种默认使用该账本最近一次使用的币种；位置只能用于展示候选币种，不能在无提示时改变用户选择。
- 保存按钮旁显示校验结果，例如“3 人均分，每人约 ¥42.67”。
- 保存成功后提供短时“撤销”，撤销实质为作废刚创建的版本。

### 13.2 编辑

- 编辑页展示“由谁于何时创建、最后由谁修改”。
- 改金额、付款人、参与者、分摊或汇率时，保存前显示余额影响摘要。
- 已产生相关还款后仍允许更正原始记录，但必须提示“将导致已结算成员重新出现余额”。
- 若同一交易在其他设备已被修改，不能用最后写入静默覆盖；应展示字段差异并让用户重新确认。
- Expense 与 Income 可以在高级编辑中互换，但必须重新确认实付/实收与应承担/应得数据；Transfer 不能直接转换为其他类型，必须作废原转账后新建正确记录。
- 编辑历史记录时，原有的停用成员继续显示并可保留；不能把停用成员新增到此前与其无关的交易中。

### 13.3 作废与恢复

- 作废前展示它会使哪些成员的余额发生多少变化。
- 已作废记录在默认列表隐藏，在“活动记录/已作废”中可查看。
- 有权限的用户可恢复到作废前版本。
- 附件应跟随修订记录保留必要的审计关联，但按隐私保留策略最终清除。

### 13.4 分类、备注与附件

- 预置分类为：餐饮、交通、住宿、购物、娱乐、生活缴费和其他；账本管理员可以增加、改名、排序和停用自定义分类。
- 分类只影响筛选和统计，不参与余额计算。分类被停用后，历史记录保留原分类，新交易不能再选择。
- 备注为账本成员可见，不应填写银行卡号、证件号等敏感信息；分享付款请求时默认不带完整备注。
- 每笔交易支持多张收据或现场照片；上传状态为 `LOCAL_ONLY`、`UPLOADING`、`READY` 或 `FAILED`。
- 交易保存与附件上传相互独立。上传失败显示明确状态并允许重试、替换或删除，不能重复生成交易。
- 照片默认仅账本成员可见；下载原图和保存到系统相册必须由用户主动操作。
- 作废交易的附件在账本删除冷静期或数据保留期限结束后清除；活动记录只保留不可反推原图的附件事件。

## 14. 离线与同步

### 14.1 基本策略

- 本地保存最近访问账本、参与者、交易快照和待同步队列。
- 每个离线写操作生成全局唯一 `operation_id`，服务端按该 ID 幂等处理。
- 客户端重试只能得到同一个结果，不能重复新增交易。
- 每次成功同步返回新的 `ledger_version` 和服务端时间。

### 14.2 合并规则

| 场景 | 处理 |
| --- | --- |
| 两人离线各新增一笔不同交易 | 两笔都保留 |
| 同一设备重复提交同一操作 | 通过 `operation_id` 去重 |
| 两人同时编辑同一交易的不同字段 | 展示冲突，可提供字段级合并建议 |
| 两人同时编辑同一字段 | 不自动覆盖，要求选择版本 |
| 一人编辑、一人作废同一交易 | 作废优先进入冲突状态，由用户决定恢复还是保持作废 |
| 离线操作时成员已被停用 | 保留本地草稿，拒绝入账并提示转交管理员 |

### 14.3 余额一致性

- 待同步交易可显示“预计余额”，但必须带离线标记。
- 正式余额只基于服务端已接受的交易版本。
- 同步完成后若结果变化，展示“因其他成员的新记录，余额已更新”，不能无提示跳变。

## 15. 结算与付款请求流程

1. 用户打开“余额”，查看自己应收或应付。
2. 系统基于当前版本生成推荐结算。
3. 欠款人选择一条建议，查看金额与解释。
4. 可复制金额和备注、生成不含敏感明细的文字/二维码付款请求，或选择“我已付款”。
5. 默认模式下，“我已付款”立即创建 `POSTED` 转账并改变余额，同时通知收款人。
6. 收款人认为有误时可发起争议；转账进入 `DISPUTED` 并暂时退出余额计算，直到双方或管理员选择恢复入账或作废。
7. 账本可开启“双向确认”；开启后转账先进入 `PENDING_CONFIRMATION`，收款人确认后才进入 `POSTED` 并改变余额。
8. 付款请求被撤回、过期或拒绝都不改变余额，只更新请求状态。
9. 结算金额超过当前欠款时允许记录真实转账，但必须强提醒“这会使你变为应收方”，不能自动截断用户实际支付金额。

避免社交压力的文案原则：使用“提醒”“核对”“待确认”，不使用“催债”“未还钱”等攻击性措辞。

## 16. 搜索、统计、导入与导出

### 16.1 搜索与筛选

支持按标题、成员、分类、日期、类型、金额范围和创建者筛选。搜索结果顶部展示当前筛选条件下的支出总额，但不能把它误认为账本余额。

### 16.2 统计

- 分类统计只统计 Expense；Income 独立展示，Transfer 排除。
- 所有跨币种图表使用交易保存时的基准币金额。
- 时间统计按交易的 `occurred_on` 归类；未来日期记录单独标记并可一键排除。
- 成员统计区分“实际垫付”“消费份额”和“当前净余额”，不把三者混为一个排行榜。
- 点击图表可回到组成该数字的原始交易。
- 编辑、作废或恢复交易后，统计与余额使用同一 `ledger_version` 更新。

### 16.3 导入

- v2.8 首选通用 CSV 导入，不把产品绑定到单一竞品。
- 导入必须经过“字段映射 → 参与者匹配 → 汇率确认 → 余额预览 → 正式导入”。
- 为每个源记录保存 `source_type + source_record_id`，重复导入时识别重复项。
- 无法识别的分摊不得自动猜测入账，应保留在错误清单。

### 16.4 导出

- 支持 CSV 明细与可读的结算摘要。
- 导出包含原币金额、基准币金额、汇率、付款人、参与人、最终份额、类型和状态。
- Owner 可申请包含活动日志和附件索引的完整数据包。

## 17. 通知逻辑

默认通知以下事件：

- 新交易影响到我。
- 影响到我的交易被修改、作废或恢复。
- 收到付款请求或转账确认请求。
- 我的转账被确认或拒绝。
- 我的成员身份、权限或账本状态发生变化。

不默认逐条通知与我无关的交易。每个账本可设为即时、每日摘要或静音。通知点击后必须定位到具体交易或结算记录。

## 18. 错误与边界条件

| 情况 | 产品处理 |
| --- | --- |
| 没有选择任何承担人 | 阻止保存，提示“请选择至少 1 位参与者” |
| 分摊金额与总额不一致 | 阻止保存并显示差额 |
| 付款合计与总额不一致 | 阻止保存并显示差额 |
| 付款人与承担人不同 | 允许，这是合法垫付场景 |
| 金额无法整除 | 自动分配最小单位并明确提示 |
| 成员改名 | 历史金额不变，活动记录保留旧名称 |
| 删除仍有余额的成员 | 不允许硬删除，改为停用 |
| 修改旧交易导致已结算余额变化 | 允许，但保存前强提醒并使结算建议失效 |
| 汇率服务不可用 | 允许手动输入；不能用 `1:1` 静默代替 |
| 附件上传失败 | 账务可先保存，附件独立重试 |
| 重复点击保存 | 通过幂等键只生成一笔 |
| 两人分别录入疑似同一笔支出 | 按账本、金额、币种、日期和付款人提示疑似重复，但不自动删除，由用户确认 |
| 账本总余额不为 0 | 视为严重一致性错误，停止结算并触发重算/告警 |
| 参与者达到上限 | 阻止新增，提示拆分账本或联系管理员 |
| 空账本 | 展示创建第一笔记录、添加成员和体验示例三个入口 |
| 邀请已过期或撤销 | 不泄露账本信息，提示联系邀请人获取新链接 |
| 无网络时首次打开邀请 | 说明需要联网完成首次授权，不创建半成品成员 |
| 权限在编辑期间被收回 | 保留本地草稿，拒绝入账并说明所需权限 |
| 数据不是最新版本 | 显示最后同步时间；结算前强制拉取最新版本 |
| 未来日期交易 | 明确标记并二次确认，入账后立即影响余额 |
| 转账被收款人争议 | 暂停计入余额，通知双方处理，不自动删除记录 |
| 服务计划维护 | 提前展示维护窗口；维护期间进入明确的只读/离线模式，不伪装成保存成功 |

v2.8 固定支持最多 50 人，但首要体验针对 2–12 人优化。

## 19. 隐私与安全底线

- 分享链接只暴露必要的单账本能力，支持撤销和过期。
- 敏感写操作使用服务端权限校验，不能依赖客户端隐藏按钮。
- 附件使用私有存储和短时授权地址，不生成永久公开 URL。
- 活动日志不可由普通成员删除。
- 账本删除采用 30 天冷静期；冷静期内 Owner 可恢复，期满后清除业务数据和附件，只保留法律或安全要求的最小审计信息。
- 用户可导出和删除自己的账户数据，但共享账本中的交易需兼顾其他参与者的合法账务记录；账户删除后可匿名化显示。
- 金额、成员关系、邀请 token 和付款备注不得出现在分析日志明文中。

### 19.1 无障碍与本地化

- 交互与视觉实现以 WCAG 2.2 AA 为基线，并遵循 iOS/Android 的辅助功能规范。
- 正负余额不能只靠红绿区分；必须同时提供文字、符号和图标。
- 支持系统字体缩放、屏幕阅读器标签、键盘焦点顺序和至少 44×44 pt 的移动点击区域。
- 金额按币种和用户地区格式化，但数据库与 API 保持统一整数语义。
- 中文界面优先使用“谁付了”“谁参与”“你需付/你应收”，避免借方、贷方等会计术语。
- 长姓名、emoji、从右到左语言和复数规则不得破坏金额对齐；昵称展示可截断，但详情必须能看到全名。
- v2.8 首发 `zh-CN`、`zh-TW` 和 `en`，所有用户文案走本地化资源，不把字符串写死在业务逻辑中。
- 主题支持“跟随系统、亮色、暗色”，默认跟随系统；所有主题都必须满足相同的对比度与金额可读性要求。

### 19.2 性能与容量门槛

- 单账本上限确定为 50 名参与者、10,000 笔有效交易；超过时允许只读、导出和归档，引导创建新账本。
- 在上述上限内，余额重算与结算建议服务端 P95 小于 500 ms。
- 正常网络下新增交易确认 P95 小于 1 秒；离线保存必须即时完成并清楚标记待同步。
- 在线状态的协作更新目标为 3 秒内到达其他成员；超过时显示最后同步时间并支持手动刷新。
- 明细采用游标分页；分页、筛选或切换设备不能改变同一版本下的排序结果。

### 19.3 可观测性与质量门槛

- 监控同步失败率、队列滞留时间、冲突率、汇率失败率、结算耗时和账务不变量失败数。
- `Σ余额 != 0`、重复入账或已作废交易参与计算属于发布阻塞级错误。
- 日志只记录匿名技术标识和错误码，不记录账本标题、成员昵称、金额、备注、附件内容或邀请 token。
- 计算引擎必须使用确定性单元测试、随机属性测试和历史回归样本；同一输入在所有平台输出完全一致。
- 无网络、慢网络、重复提交、跨设备冲突、时区切换和汇率失败必须进入发布前测试矩阵。

## 20. v2.8 功能范围

P0 与 P1 合在一起构成 v2.8 的公开发布范围；P0 是可进行真实账务测试的闭环，P1 是发布前必须完成的完整体验。P2 已明确排除，不属于文档遗漏。

### 20.1 必须完成（P0）

- 账本创建、冻结、归档和恢复。

## 22. 已定案的产品决策

以下规则作为 v2.8 默认行为，不再保留开放分支：

1. **Guest 权限**：持有效编辑邀请的 Guest 可以查看并新增自己的记录，不能编辑他人记录、管理成员或更改账本设置；只读邀请只能查看。
2. **他人记录修改**：Member 默认只能修改/作废自己创建的记录；Owner/Admin 可以处理全部记录。Owner 可显式开启“成员共同纠错”。
3. **手动还款**：默认标记已付款后立即入账并通知收款人；收款人可发起争议。需要更严格控制的账本可以开启双向确认。
4. **多付款人**：纳入 v2.8 P0，但放在“高级：多人付款”入口；常规新增仍默认单付款人。
5. **汇率**：通过可替换的数据源适配器获取每日市场中间价，保存来源、日期和汇率快照；离线可使用最近 72 小时快照并明确标记，超过 72 小时必须手动确认或输入。永不静默使用 1:1。
6. **逐项分摊**：数据模型预留，v2.8 不提供 UI，归入 P2；这不影响金额级自定义分摊的完整性。
7. **人数与容量**：单账本上限固定为 50 人、10,000 笔有效交易。
8. **未来日期**：未来日期的已付款交易立即入账并影响余额，不等同于计划任务；周期性账单归入 P2。
9. **账本删除**：统一采用 30 天可恢复冷静期；期满后执行删除或必要的匿名化保留。
10. **支付集成**：v2.8 只记录账务和分享付款请求，不声称已真实到账；只有用户确认或未来可信支付回调才能生成有效转账。
11. **首次创建与分享**：允许无账号用户在本机体验未分享账本；生成邀请、跨设备同步或完整导出前必须升级为已验证 Owner。
12. **客户端范围**：产品逻辑和计算协议保持平台无关，交互以手机为第一优先级；Web、PWA 或原生客户端必须共享同一服务端权限和计算规则。
